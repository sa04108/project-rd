# 과금 도입 전 데이터 변조 점검

점검일: 2026-10-03 (한국 시간). 게임 코드 기준: `83e7c3c` (`feat/permanent-progression`, `devel`에서 이어진 작업). 이 문서는 공격 경로와 개선 요구를 기록하며 게임 코드의 보안 수정은 포함하지 않는다.

## 결론

**현재 로컬 다이아몬드 지갑을 유료 재화의 원본으로 사용하면 안 된다.** 잔액만 수정하는 단순 변조는 거부하지만, 원장·잔액을 함께 수정하면 실제 구매까지 통과한다. 전투 저장에 기록된 영구 단계와 보상 근거 역시 사용자가 바꿀 수 있다. 현재 검증은 저장 데이터의 형식·내부 일관성 검사이며 지급·구매의 진위 인증이 아니다.

실제 결제와 계정 서버는 아직 구현되지 않았다. 따라서 실제 결제 API 침투, 영수증 재사용, 타 계정 접근을 검증한 결과는 아니다. 아래 P0 항목을 만족하기 전에는 결제를 활성화하지 않는다. 오프라인 전투의 모든 수치 조작을 차단하는 것과 서버의 유료 잔액·소유권을 보호하는 것은 별도 목표로 정한다.

## 도구와 실증 범위

**Codex Security 0.1.31**의 `security-scan` 실행 준비 검사는 `ready`였다. 그러나 정식 스캔 시작 도구는 `Starting a Standard scan requires the owning Codex thread context.`로 거부했다. 연결 정보나 스캔 ID를 임의로 만들지 않았다. 플러그인의 `references/artifact-storage.md` 지침은 “If the required MCP is unavailable or the selected baseline is unsupported, report the blocker; do not fall back to shell-authored canonical files.”라고 규정한다. 따라서 전체 저장소 정식 스캔·봉인된 보고서가 완료된 것으로 표기하지 않는다.

대신 같은 플러그인의 **`propose-security-hardening` 스킬**을 적용해 직접 재현 자료와 `83e7c3c`의 실제 저장·보상·전투 복원 코드를 대조하고 설계 대안을 분석했다. 이 스킬은 정식 스캔 없이 기존 점검 자료를 입력으로 받을 수 있다. 아래 A01~A10은 로컬 점검에서 직접 재현한 결과이며 플러그인이 새로 실행한 침투 실험이 아니다. 스킬의 근거 분류·반증·대안 비교를 반영한 결론과 개선 항목을 이 문서에 남긴다.

격리한 테스트 저장과 브라우저 프로필만 사용했다. 실제 사용자 데이터, 공개 서비스, 실제 결제는 건드리지 않았다. APK·Web 내보내기는 기존 설정을 사용했고 공격 코드는 제품 코드에 넣지 않았다.

## 플랫폼별 추가 노출

- **Web:** `/userfs` IndexedDB의 `FILE_DATA`에 저장된 프로필·전투 데이터는 같은 브라우저 사용자가 읽고 쓸 수 있다. JS/Wasm과 PCK도 클라이언트에 내려간다. IndexedDB를 암호화하거나 JavaScript를 숨기는 것을 유료 잔액의 신뢰 근거로 삼으면 안 된다. 다른 출처 사이트가 이 DB를 자동으로 수정할 수 있다는 의미는 아니며, 이번 점검에서 XSS나 타 계정 탈취를 발견한 것은 아니다.
- **Windows:** 확인한 기본 경로는 `%APPDATA%\Godot\app_userdata\project-rd · 용병 길드`다. 자기 계정의 저장 파일은 편집·복원 가능하다. Windows용 배포 설정, 코드 서명, 실제 Windows에서의 프로세스 메모리 쓰기·DLL 주입·패치 프로그램 재실행은 아직 검증하지 않았다.
- **Android:** 현재 산출물은 **디버그 APK**이며 `debuggable=true`, Godot 기본 디버그 인증서, `allowBackup=false`를 확인했다. 같은 상황의 개발 빌드에서는 승인된 ADB의 `run-as` 접근이 예상되지만 **이 APK에서 실행해 확인하지는 못했다**. 정상 비루팅 release 앱의 다른 앱이 내부 저장을 자유롭게 편집할 수 있다고 단정하지 않는다. 루팅·후킹·재패키징 경로는 별도 실증이 필요하다.
- **개발 기능:** [main.gd](../game/main.gd)의 `dev_mode`는 `--dev` 시작 인자만 검사하며 release 여부를 검사하지 않는다. F8은 웨이브 이동과 골드 500을 적용한다. `developer_run`은 영구 보상·최고 기록에서 제외되지만 저장 파일의 bool을 바꾸는 것을 막지는 않는다. 실제 Web release에서 시작 인자를 추가한 뒤 웨이브 11·골드 650이 되는 것과 저장의 개발 표식을 확인했다(A10).
- **패키지:** [export_presets.cfg](../export_presets.cfg)는 PCK·디렉터리 암호화를 사용하지 않고 Android에 `--android-qa` 인자를 넣는다. 읽을 수 있는 리소스·규칙은 역분석 비용을 낮춘다. 다만 패키지 암호화, 난독화, 로컬 비밀키 추가만으로 지급·구매 인증을 대체할 수 없다. 클라이언트 키와 검증 코드는 패치·추출의 대상이다.

메모리 편집·동적 후킹·패키지 변조 실행·실제 구매 서버 공격까지 전부 성공했다고 주장하지 않는다. 저장 변조만으로 이미 경제 보호가 우회되어, 우선 신뢰 경계를 바꾸는 것이 필요하다.

| ID | 개선 항목 | 완료 기준 |

## Codex Security 보안 강화 설계

실제 코드를 다시 확인한 결과, 핵심은 파일 암호화 여부보다 **재화의 최종 판정을 누가 소유하는가**에 있다. `game/save_store.gd:223`의 원장 검사는 같은 파일에 담긴 수치끼리 비교하고, `:287`의 구매는 그 로컬 지갑을 차감한다. `:322`의 보상은 로컬 최고 기록과 전투 결과를 사용한다. `game/simulation.gd:537`은 형식 검사를 통과한 전투의 영구 단계를 그대로 복원한다. 줄 번호는 실증 기준 `83e7c3c`이며 이후 용병 합성 제거로 현재 simulation의 줄 위치는 달라졌다.

현재는 계정·결제 서버가 없는 단독 게임이므로 자기 저장을 고치는 행위를 타 계정 침해나 운영 결제 서버 취약점으로 과장하지 않는다. 다만 우리가 앞으로 같은 값을 유료 잔액과 연결하면, 클라이언트 소유 값이 서버의 지급·구매 권한으로 바뀌는 지점에서 문제가 생긴다. 아래는 구현 전 선택할 설계이며 보안 수정 완료를 뜻하지 않는다.

| 대안 | 재화와 보상의 최종 판정 | 효과·남는 위험 | 주요 비용·조건 |
|---|---|---|---|
| 1. 로컬 검증 보강·과금 보류 | 현재처럼 기기 내부 | 손상·오래된 쓰기는 줄일 수 있지만 원장 동시 변조·후킹을 인증할 수 없음 | 오프라인·즉시 반응 유지. 유료 재화 도입 조건을 충족하지 못함 |
| 2. 서버 지갑·구매, 오프라인 보상 분리 | 서버가 영수증·구매·영구 소유권 확정. 검증 불가능한 전투 보상은 서버 다이아몬드로 전환하지 않음 | A01·A02·A07~A09의 서버 경제 전파를 막음. 로컬 전투 수치 조작은 남음 | 구매 시 통신, 계정·원장·환불 운영 필요. 현재 전투 보상 정책을 바꿀지 사용자 결정 필요 |
| 3. 서버 지갑·구매·검증 가능한 전투 보상 | 서버 전투 세션과 권한을 연결하고 실행 또는 입력 재검증 뒤 보상 확정 | 현재 전투 다이아몬드 획득을 유지하면서 A03~A06까지 막는 목표. 클라이언트 결과 서명·상한 검사만으로는 부족 | 전투 판정 호환성, 검증 CPU·입력 보관, 동기화·장애 복구 부담 증가 |

**현재의 전투 다이아몬드 보상을 유지하려면 3안을 목표로 권고한다.** 출시 범위와 운영비를 먼저 줄여야 한다면 2안도 합리적이지만, 오프라인 보상을 다른 경제로 분리하는 정책에 먼저 동의가 필요하다. 이번 작업에서는 보상 정책이나 서버 구조를 변경하지 않았다. 1안은 과금을 열지 않는 동안 사용할 기준선이다.

새 구조의 합격 조건은 변조 저장·중복 요청·타 계정 토큰·환불·동시 기기·옛 저장 복원이 서버 잔액과 소유권을 바꾸지 못하는 것이다. 우리는 정상 신규 구매와 재시도도 함께 확인해야 한다. 네트워크 실패 시 로컬 값으로 지급을 대신하지 않고 요청 ID로 확정 상태를 다시 조회한다. 기존 로컬 다이아몬드는 서버 잔액으로 1:1 승격하지 않는다. 과거 가격 이력은 거래 당시 서버가 확정한 정책 버전으로 보존한다.

성능·메모리 비용은 아직 측정하지 않았다. 2안은 구매·조회 왕복과 DB 트랜잭션, 3안은 이에 전투 검증 CPU·입력 보관이 더해진다는 소스 기반 예상이다. 실제 구현 전에 구매 지연 p95, 동시 거래 충돌률, ×20·100웨이브 결과 검증 시간, 전투당 보관량의 허용치를 정하고 측정한다. 전환 실패 시 과금·지급을 중단하고 서버 원장을 유지하며, 로컬 지갑을 권위 저장소로 되돌리지 않는다.
